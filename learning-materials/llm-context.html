大模型的上下文（Context / 上下文窗口）

一句话定义：上下文是模型在一次推理中“能看到的所有文本”，以 token 为单位，受上下文窗口上限约束；它决定了模型能利用多少前文来生成回答。

① 学习目标

  • 能解释 token 与上下文窗口的关系。
  • 能说明“上下文不够”会导致什么问题。
  • 能说出管理长上下文的常用策略（检索 / 摘要 / 分块）。

② 核心问题

  • 上下文窗口越大越好吗？为什么有上限？
  • 模型“记住前文”靠的是什么机制（注意力）？
  • RAG / 摘要是如何缓解上下文不足的？

③ 个人化概念解释

把上下文想成模型眼前的“工作台”。你每次对话，模型并不是真的“记得”你，而是把本次对话里所有历史 + 系统设定 + 新提问拼成一个长文本，一起喂给模型。它只看得到这块“工作台”上的内容。超出窗口的部分会被丢弃或压缩——所以模型会“健忘”，本质是工作台放不下了。

这不是模型的记忆问题，而是输入长度的工程约束。所谓“长期记忆”，几乎都是应用层用数据库帮模型把旧信息在需要时重新搬回工作台。

④ 核心机制 / 组成结构

  • Token：文本被切成的的最小单位（词 / 字片段），计费与长度都按 token 算。
  • 上下文窗口（Context Window）：单次推理可容纳的最大 token 数（如 8K / 128K）。
  • 注意力机制（Attention）：Transformer 让每个 token 都能“关注”前文相关 token（见《Attention Is All You Need》），这是模型利用上下文的方式。
  • 上下文的构成：通常 = 系统提示 + 历史消息 + 检索注入 + 当前提问。

⑤ 具体应用场景

场景超长合同问答

输入：针对 200 页合同提问。

处理：直接把整本合同塞进上下文会超限且昂贵。做法：先切片 + 向量检索，只把最相关的 3 段塞进本次上下文，让模型基于这几段回答。

输出：精准答案，且成本与延迟可控。这正是用“检索补全上下文”代替“无限扩大窗口”。

⑥ 概念辨析、使用边界与易混淆知识点

上下文 ≠ 长期记忆：模型默认不跨会话保存；所谓“记忆”多是应用层用数据库模拟，在需要时再搬回上下文。

上下文 ≠ Prompt：Prompt 通常指“单次指令文本”；上下文是本次推理里被拼接进窗口的全部文本（系统设定 + 历史 + 检索 + 当前提问），Prompt 只是上下文的一部分。

上下文 ≠ 训练数据 / 参数记忆：训练数据在预训练阶段固化进参数；上下文是推理时临时喂入的内容。模型“知道”某事可能来自参数，也可能来自本次上下文，二者要分清。

窗口大 ≠ 用得好：过长上下文会引入噪声、拖慢速度、增加成本，且注意力可能被稀释（“中间遗忘”现象）。

易混淆小结：参数记忆 = 模型脑子里背的；上下文 = 这次摊在工作台上的纸；Prompt = 其中你写的一张便条。

边界：超过窗口必须靠检索 / 摘要补全；把敏感信息放进上下文会带来泄露风险，需注意脱敏。

⑦ 自测问题

  1. 为什么“模型忘了前面的话”通常是上下文窗口 / 拼接策略问题，而不是模型真的有记忆？
    提示：模型无跨轮记忆，靠本次输入拼接；超窗口即被截断。
  2. 注意力机制如何解决“长距离依赖”？
    提示：每个 token 可直接关注远距离相关 token，不必逐字传递。
  3. 什么场景应优先用 RAG 而不是无限扩大上下文？
    提示：知识库巨大、需控制成本、且只需相关片段时。
参考答案（点击展开）
  1. 答：模型本身不跨会话保存信息；它每次只“看”本次被拼进窗口的文本。所谓“忘了”，是拼接策略把旧内容挤出窗口或被截断，并非模型有记忆后丢失。
  2. 答：Transformer 的注意力让任意两个 token 直接建立关联，模型可在生成时直接“回头看”远距离的相关前文，不必靠逐字顺序传递，从而缓解长距离依赖。
  3. 答：当知识库极大、只需其中相关片段、且要控制成本与延迟时，RAG 用检索把少量相关文本注入上下文，比把整库塞进窗口更省、更准。
